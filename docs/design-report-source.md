# 基于大语言模型与多智能体协作的电路板设计系统

## 摘要

本报告设计并实现了一个从自然语言需求出发、自动产出可打开、可校验的 KiCad 原理图与 PCB 的电路板设计智能体系统。系统的核心判断是：大语言模型不适合直接生成 KiCad 文件，而适合生成**结构化中间表示**。据此，本系统把整个流程切成"模型提议、代码把关"两段：模型只输出器件清单与引脚级连接表（IR），由确定性渲染器把 IR 变成 `.kicad_sch`，再由规则校验器、`kicad-cli` 的 ERC/DRC 与 ngspice 仿真分别从结构、连接、电气行为三个层面验证，发现问题后以原子补丁的形式回灌给模型返修。

系统实现了课程要求的全部五个基础步骤，并完成四项进阶挑战：多智能体协作、DRC 检查闭环、自动布局布线、仿真评测。实测结果：一句话需求生成 18 个器件、11 条网络、48 个连接点的 Arduino 最小系统板，原理图导出的网表与 IR 逐引脚一致（48/48），ERC 0 错误；自动布线 11/11 网络全部布通，PCB DRC 0 错误；工作点仿真得到 +5V 轨 5.0000 V、指示灯电流 2.936 mA，与手算一致。

为验证各设计选择是否真的有效，本文做了两组对照实验。第一组 8 个需求 × 4 种配置的消融实验给出一个**对本方案不利但重要的负结果**：不带校验工具的"盲评审"多智能体配置平均残留 1.75 个错误，比完全不返修（1.00 个）还差；而纯规则修复与带工具评审同样达到零错误，成本却只有后者的一半。第二组补充实验构造了结构校验无法发现的"值错误"（连接完全正确、仅电阻值错误），证明只有把仿真结论接入返修闭环的配置才能发现并修复此类问题。这两组数据共同指向一个结论：多智能体的价值不取决于角色数量，而取决于**是否给评审者提供了能发现功能错误的工具**。

**关键词**：大语言模型；多智能体；电子设计自动化；KiCad；SPICE 仿真；中间表示

## 1 需求分析

本章先把课程要求翻译成可执行、可验收的系统需求，再由此推导出贯穿全系统的三条设计原则。

### 1.1 任务背景与约束

课程任务要求在八周内构建一个可用的电路板设计 Agent，并给出明确的验收口径：基础任务五步（环境搭建、自然语言到 BOM、连接关系生成、导入 KiCad 生成原理图、支持追问改需求）共 40 分；进阶挑战任选其一（多智能体协作、DRC 闭环、自动布局布线、仿真评测）共 20 分；设计报告 20 分；答辩 10 分；过程表现 10 分。交付物为代码仓库（含 README）、设计报告、3 至 5 分钟演示视频与答辩 PPT。

这些约束直接决定了设计取向。第一，**八周的周期不允许做通用 EDA 工具**，必须把范围收窄到一个能演示完整的闭环；第二，**评分看"架构讲得清、实验有数据"**，说明系统不仅要能跑，还要能被解释、被度量、被复现；第三，**报告要求包含失败案例分析**，意味着"一路成功"的叙事反而不符合要求，系统必须留下可分析的失败痕迹。

### 1.2 功能需求

把课程的五步翻译成可执行的系统需求：

| 编号 | 需求 | 验收方式 |
|---|---|---|
| F1 | 输入一句中文需求，输出结构化的板级规格与器件清单 | 输出 `design.json`，含 BOM 与引脚级网表 |
| F2 | 连接关系必须是结构化的、可被程序检查的 | 每根连接表示为 `位号.引脚号`，网络带类型（电源/地/信号） |
| F3 | 产物能直接用 KiCad 打开，且电气正确 | `kicad-cli` 导出网表与 IR 一致、ERC 零错误 |
| F4 | 支持追问修改，且只改被要求的部分 | 修改以补丁形式落盘，可审计、可回放 |
| F5 | 发现错误后能自行返修，而不是把错误交给人 | 校验发现问题后自动生成补丁并重跑校验 |
| F6 | 产物可复现 | 同一输入生成同一份文件（除时间戳），温度固定为 0 |

### 1.3 非功能需求

除功能之外，还有四条工程约束，它们在后文反复出现：

1. **零必需依赖**。除 Python 标准库外不引入运行时依赖，保证助教按 README 能在五分钟内跑起来。这条约束后来直接决定了仿真方案的选择（见 2.5 节）。
2. **可验收**。每一个"完成"都要有机器可读的证据，而不是"看起来对"。因此所有校验结果都落成 `Issue` 结构，最终写进 `summary.json`。
3. **成本可控**。一次设计应控制在个位数的大模型调用内，否则既贵又慢，也无法做批量实验。
4. **诚实降级**。缺少 KiCad、缺少 API Key、缺少仿真库时，系统应明确说明跳过了什么，而不是静默通过。

### 1.4 从需求到三条设计原则

上述需求推导出三条贯穿全系统的原则，它们不是口号，而是可以被代码检查的约束：

**原则一：模型只产出 IR，绝不直接写 KiCad 文件。** 让模型拼 s-expression 是最常见的失败来源——它会编出不存在的引脚、错的 UUID、格式非法的括号。把模型的输出限定为"器件 + 值 + 连接"这种 JSON，再由确定性代码渲染，成功率会高一个数量级。

**原则二：引脚要"喂"给模型，而不是"问"模型。** 把器件库中真实的引脚号列表注入提示词，只允许模型从枚举中选择，可以消掉绝大部分引脚幻觉。

**原则三：校验必须是代码，不能是"另一个模型看一眼"。** 电源轨是否唯一、每个引脚是否只属于一个网络、去耦电容是否覆盖每个电源脚，这些都能写成几十行规则函数。5.7 节的实验证明，把校验交给模型（盲评审）不仅无效，还会主动制造错误。

## 2 系统架构

本章先给出分层结构与核心数据结构，再说明执行链、多智能体协作形态，以及技术路线与后端选型。

### 2.1 分层结构

系统自下而上分为五层，层与层之间只通过数据结构通信，不共享隐式状态。

| 层 | 职责 | 主要模块 | 依赖 |
|---|---|---|---|
| 契约层 | 定义唯一的数据结构 | `ir.py`（BoardSpec / BomItem / Net / DesignIR / Issue） | 无 |
| 生成层 | 把 IR 变成各类产物 | `subcircuits.py`、`render.py`、`pcb.py`、`router.py`、`spice.py` | 契约层 |
| 校验层 | 从三个层面判定对错 | `validate.py`（规则）、`kicad_gate.py`（ERC/DRC/网表）、`simcheck.py`（电气行为） | 契约层 |
| 编排层 | 组织闭环与返修 | `orchestrator.py`、`agents/`、`patch.py` | 以上各层 |
| 输出层 | 落盘与展示 | `__main__.py`、`simulate.py`、`trace.py` | 编排层 |

分层的收益在开发后期非常明显：当我把验证从"导出网表再比对"换成"直接调 KiCad IPC"时，只动了校验层的一个后端开关，编排逻辑一行未改。

布线结果保存在 `runs/pcb-demo2/board.kicad_pcb`，其 KiCad 3D 预览（`kicad-cli pcb render` 渲染，未加载器件 3D 模型）另存于仓库 `docs/figures/board-3d.png`，可直接用 KiCad 打开复核。

### 2.2 核心数据结构：IR 是唯一契约

`DesignIR` 只有三个字段：`spec`（板级规格）、`bom`（器件清单）、`nets`（网络表）。其中网络表的成员统一表示为 `位号.引脚号`，例如 `U1.7`，而不是引脚名——因为真实引脚名可能包含 `~RESET/PC6` 这类对程序不友好的字符。

这个看似简单的决定带来了三个好处：其一，网表可以被独立校验，不需要解析任何 KiCad 文件；其二，同一个 IR 可以渲染成原理图、PCB、SPICE 网表三种产物，三者天然保持同步；其三，任何修改都退化为对 IR 的编辑，可以完整记录成 diff。

`DesignIR.structural_issues()` 在构造阶段就做自检：位号是否重复、成员格式是否合法、网络是否为空。把最基本的一致性检查放在数据结构内部，避免了下游到处写防御性判断。

### 2.3 执行链与闭环

主流程是五个节点的循环：

```
需求分析 → 电路设计 → [渲染 + 规则校验 + ERC + 仿真] → 评审 → 补丁 → 回到校验
   ↑                                                                    │
   └────────────────────── 最多 3 轮，收敛即停 ─────────────────────────┘
```

各节点的输入输出都是结构化数据，不传递自由文本对话：

| 节点 | 输入 | 输出 | 是否调模型 |
|---|---|---|---|
| 需求分析 Analyst | 一句话需求 | `BoardSpec`：功能、电源轨、接口 | 是（可降级为规则） |
| 电路设计 Designer | `BoardSpec` + 上轮问题 | `DesignIR` | 是（选子电路 + 填参数） |
| 校验（工具节点） | `DesignIR` | `.kicad_sch`、网表、ERC、`sim.json`、`Issue[]` | 否，纯代码 |
| 评审 Critic | 需求 + 产物 + 校验报告 | `PatchOp[]` | 是 |
| 应用补丁（工具节点） | `DesignIR` + `PatchOp[]` | 新 `DesignIR` | 否，纯代码 |

关键设计是**校验节点不是模型**。它是三个确定性工具的聚合：11 条电气规则、`kicad-cli` 的网表/ERC、ngspice 的电气断言。评审节点拿到的是这些工具的结构化输出，而不是"让模型自己看看对不对"。

### 2.4 多智能体协作的实质

本系统没有采用"多个模型自由对话"的形态，而是让多个角色操作同一份共享状态，中间夹着确定性工具。三个角色的差异体现在三处，而不是只换个名字：

| 角色 | 专属输入 | 专属输出 | 工具白名单 | 温度 |
|---|---|---|---|---|
| Analyst | 用户原话 | `BoardSpec` | 器件检索（只读） | 0 |
| Designer | `BoardSpec` | 子电路选择 + 参数 | 器件库引脚表、子电路模板 | 0 |
| Critic | 校验报告 | `PatchOp[]` | 必须能读校验结果 | 0 |

两条硬规则：**其一，评审必须带工具**，否则就是两个模型互相恭维，5.7 节的实验数据证实了这一点；**其二，回灌的是补丁而不是"重写一遍"**，用 6 个原子操作（改值、加器件、删器件、连接、断开、改名）表达修改，应用后重跑校验。

这套机制同时解决了基础第 5 步"把电容换成 100nF"——那是一次 `set_value` 补丁，不是重新生成整块板。

### 2.5 技术路线选型与对比

实现路径上有三条可行路线，本系统选择了第三条，但吸收了前两条的部分做法：

| 维度 | A：进程内 libngspice | B：独立 ngspice 命令行 | C：自写求解器 |
|---|---|---|---|
| 依赖 | 零新增（KiCad 自带 DLL） | 需另装二进制并配 PATH | 零新增 |
| 能力 | 支持非线性、瞬态、交流分析 | 同 A | 仅线性直流 |
| 崩溃隔离 | 需自行做子进程 | 天然隔离 | 天然隔离 |
| 结论 | **采用** | 留作可选后端 | 仅作无 KiCad 环境兜底 |

选 A 的决定性理由是两条实测事实：本机 KiCad 的 `bin/` 下只有 `ngspice.dll`，没有 `ngspice.exe`；环境里也没有 numpy、PySpice、SciPy。在"零必需依赖"的约束下，用 ctypes 直连 KiCad 自带的 libngspice 是唯一不引入新依赖又保留 SPICE 精度的方案。代价是必须自己做进程隔离，因为 libngspice 出错时是访问违例而不是 Python 异常，会直接杀掉宿主进程。

与开源方案 KiCAD-MCP-Server 的对比也影响了架构。该项目的做法是把 KiCad 的 122 个能力包装成 MCP 工具，由模型逐步调用，人在旁边看着改。两条路线的根本差异是"真值存在哪"：它存在 KiCad 进程的内存里，本系统存在可 diff 的 IR 文件里。前者适合交互式改板与教学演示，后者适合批量生成与可评测的流水线。因此本系统没有整体迁移到 MCP 路线，但吸收了两点：用 IPC 把产物推送到运行中的 KiCad（`kicad_live.py`），以及接入 KiCad 官方符号库（`official.py`，可读 223 个库）。

### 2.6 与 KiCad 的三种对接后端

为了兼顾"可复现"与"能演示"，系统把 KiCad 对接做成三档可切换：

| 后端 | 谁在干活 | 擅长 | 局限 |
|---|---|---|---|
| `cli`（默认） | `kicad-cli` | 批量、可复现、可进 CI | 看不见图形界面 |
| `live` | KiCad IPC API | 把产物推到人眼前 | 原理图没有对象模型，ERC 仍须走 cli |
| `off` | 无 | 无 KiCad 环境也能跑 | 无网表/ERC 交叉验证 |

`live` 后端的实测边界值得记录：KiCad 10.0.7 配合 kipy 0.7 时，`get_version()` 正常，但 `get_open_documents()` 与 `get_board()` 一律返回 `no handler available`；尝试过 `os.startfile`、`eeschema.exe` 直接打开、生成 `.kicad_pro` 后启动工程管理器三种方式，均无法让 IPC 建立文档级处理器。根因是 IPC 的处理器挂在编辑框上，且 kipy 只暴露 PCB（Board）对象，没有原理图对象模型。因此该后端最终定位为"推送 + 状态上报"，而不是"接管校验"。这个失败本身是有价值的：它说明把 IPC 当主路径并不现实。

## 3 Prompt 设计

本章说明三份角色说明书如何划分职责，以及用哪几道闸门抑制幻觉、约束修改范围、保证结果可复现。

### 3.1 三份角色说明书的职责边界

提示词不是一段万能指令，而是三份职责互斥的工作说明书，每份都明确写出"你不做什么"：

| 角色 | 系统提示词的核心约束 | 输出格式 |
|---|---|---|
| Analyst | 只做需求解析，不选器件；不确定的约束要写进 `constraints` 而不是猜 | 单个 JSON 对象 |
| Designer | 只做选择题（从子电路模板中选）与填空题（参数），**不写引脚号** | `{"subcircuits": [{"id", "params"}]}` |
| Critic | 只输出最小补丁，**不许重写整个设计**；改不动就说明原因 | `{"patches": [...], "reasoning"}` |

把"不做什么"写进提示词，比写"要做什么"更有效。例如 Designer 的提示词明确禁止输出引脚号，因为引脚号由模板和器件库决定，模型一旦插手就必然出错。

### 3.2 四道抑制幻觉的闸门

模型幻觉在电路场景里是致命的——编一个不存在的引脚，产物就是一块废板。系统设了四道闸门，逐层收窄：

1. **枚举而非生成**。Designer 只能从子电路模板列表中选，不能自创电路拓扑。
2. **引脚白名单注入**。需要模型判断引脚时，把器件库中的真实引脚表（含引脚号、名称、电气类型）拼进提示词，只允许从枚举中选。
3. **结构校验兜底**。即使模型给了不存在的引脚号，`validate.py` 的 `PIN_NOT_EXIST` 也会拦截，并在返回值里指出是哪个位号的哪个引脚。
4. **JSON 解析失败即回灌重试**。客户端把解析错误原文回灌给模型重试一次，而不是抛异常终止。

这四道闸门的效果可以量化：在 8 个用例 × 4 种配置的消融实验中，**引脚幻觉数为 0**。但这不等于模型不会犯错——5.1 至 5.3 节的三个真实案例说明，它换了一种方式出错：不是编引脚，而是编器件库名、编位号。

### 3.3 补丁协议：回灌修改而不是重写

评审的输出被限定为 6 种原子操作：

| 操作 | 语义 | 典型场景 |
|---|---|---|
| `set_value` | 改器件值 | "把 C3 换成 100nF" |
| `add_part` | 新增器件 | "加一颗 10uF 储能电容" |
| `remove_part` | 删除器件 | 评审发现多余器件 |
| `connect` | 把引脚接入网络 | 补去耦电容后接线 |
| `disconnect` | 从网络移除引脚 | 断开错误连接 |
| `rename_net` | 重命名网络 | 语义化命名 |

补丁机制带来三个工程收益：修改可审计（每步都有 diff）、可回放（`trace.jsonl` 记录全部操作）、可原子化（见 5.1 节的两阶段执行）。

### 3.4 过度设计护栏：以用户原话为准

实测中发现模型有明显的"过度设计"倾向：用户只要最简最小系统，它也会加上指示灯与传感器接口，导致选型准确率只有 50%。仅靠提示词加一句"不要过度设计"只能救回个别用例，因此在 Designer 之后加了一道确定性护栏 `_prune_unsupported`：每个可选子电路必须有需求文本作为依据，否则剔除。

关键细节是**依据必须是用户原话，而不是需求分析的结果**。因为 Analyst 会"按常见做法补齐"，把指示灯写进 `functions`，若以 `BoardSpec` 为依据，护栏就形同虚设。修正后选型准确率从 50% 提升到 100%。

### 3.5 可复现性：温度与确定性

消融实验初期出现过"同一需求两次采样选出不同子电路"的现象，导致选型准确率变成噪声。因此把大模型温度固定为 0（保留 `PCB_LLM_TEMPERATURE` 环境变量以便对比），并在 `summary.json` 中记录模型名、调用次数、token 用量与耗时。

可复现的另一半来自确定性生成：子电路模板、渲染器、布线器、SPICE 网表生成器全部是纯函数，同一 IR 产生字节级相同的产物（仅时间戳与 UUID 不同）。这让"重跑实验得到同一张表"成为可能。

### 3.6 Prompt 结构示例

以评审提示词为例，其结构固定为五段，顺序不可调换：

| 段落 | 内容 | 作用 |
|---|---|---|
| 角色与禁令 | "你是电路评审专家，只输出补丁" | 限定输出空间 |
| 当前设计概况 | 器件数、网络数、连接点数 | 建立上下文 |
| 器件库目录 | 可用的 `pcbagent:*` 符号列表 | 防止编造库名 |
| 当前 BOM | 位号 \| 值 \| 符号 | 让模型知道改哪个 |
| 校验问题清单 | 逐条 `Issue`（级别、位置、原因、建议） | 提供修改依据 |

第三段是后加的——正是因为 5.1 节的失败案例（模型写了 KiCad 官方库名 `Device:C`），才把器件库目录显式塞进提示词。

### 4.5 工作点仿真与电气断言

仿真不额外安装任何软件：用 ctypes 直连 KiCad 自带的 `ngspice.dll`（ngspice-46），在子进程中执行，避免访问违例拖垮主进程。器件到 SPICE 的映射写在 `data/spice_models.json` 中，共六类：两端元件、子电路（LDO、晶振）、开关、等效负载、跳过。

工作点仿真结果与手算对照：

| 网络 | 实测 | 手算 | 判定 |
|---|---|---|---|
| VIN_RAW | 12.0000 V | 12 V 外部输入 | 一致 |
| +5V | 5.0000 V | LDO 稳压 5 V | 一致 |
| LED_A | 2.0001 V | LED 正向压降约 2.0 V | 一致 |
| RESET | 4.9999 V | 10k 与 1G 分压 | 一致 |
| 指示灯电流 | 2.936 mA | (5−2.0)/1k = 3.0 mA，再减 22Ω 驱动内阻压降 | 一致 |

此外验证了压差行为：把输入电压改为 5.5 V，输出降到 4.4 V（5.5 − 1.1），而不是继续硬撑 5 V。这说明 LDO 模型不是"永远输出 5V"的假模型，后续断言才有意义。

在数值之上建立 5 条断言，转成与结构校验同构的 `Issue`，接入返修闭环：

| 断言 | 判据 | 目标故障 |
|---|---|---|
| `SIM_RAIL_DEAD` | 电压低于期望值 50% | 稳压器未工作 |
| `SIM_RAIL_OUT_OF_RANGE` | 偏差超过 5% | 稳压值错误、压差不足 |
| `SIM_LED_OVERDRIVE` | 电流超过 20 mA | 限流电阻过小 |
| `SIM_LED_OFF` | 电流低于 0.5 mA | 电阻过大或驱动未拉开 |
| `SIM_REGULATOR_OVERHEAT` | (Vin−Vout)×Iin 超过 0.8 W | 封装散热不足 |
| `SIM_DECOUPLE_Z` | 等效电容低于设计值 70% | 去耦电容没真正并在轨上 |
| `SIM_I2C_RISE` | 上升时间超过 300 ns | 上拉太弱或总线电容太大 |
| `SIM_RESET_TAU` | 复位 RC 不在 0.5~5 ms | 复位电容过大或过小 |

后三条不是直流工作点能算出来的，各需要一种专门的分析类型；而它们的共同前提是**先给器件补模型**，否则测出来的永远是"通过"：

| 断言 | 分析类型 | 判据 | 实测（examples/design.json） |
|---|---|---|---|
| `SIM_DECOUPLE_Z` | `.ac` 扫频 + 1 A 电流注入 | 等效电容不低于设计值的 70% | +5V **529 mΩ @1 MHz**，折算 301 nF，设计值 300 nF |
| `SIM_I2C_RISE` | `.tran` 充放电 | 30%→70% 上升时间不超过 300 ns | SDA / SCL 各 **100 ns** |
| `SIM_RESET_TAU` | `.tran` 充电 | 时间常数落在 0.5~5 ms | 本板**不适用**（无复位电容） |

三处建模决策值得单独说明：

1. **电容必须带 ESR 与 ESL。** 理想电容的交流阻抗恒为 0，任何阈值都会"永远通过"。给 0603 陶瓷电容串上 12 mΩ ESR 与 0.6 nH ESL 后，阻抗才有物理意义；这两个参数不影响直流工作点（实测改前改后都是 5.0000 V、2.936 mA）。
2. **测 PDN 时把稳压器视作开路。** 理想受控源在交流分析里会把输出阻抗压到 0，等于又造一条假断言。因此只保留电容、ESR 与负载电阻，测的是"设计者能改的那部分"——电容组有没有真正形成低阻通路。
3. **判据用比值而不是绝对阻抗。** 1 MHz 下 100 nF 本身就是 1.6 Ω，写死绝对阈值会随板子规模误判；把实测阻抗折算成等效电容、与 BOM 设计值比较，才能跨板型通用。

三条断言都做过负向验证（故意改坏设计，确认能报出来）：把一颗去耦电容的接地端改接到信号网，+5V 阻抗由 529 mΩ 升到 794 mΩ、等效电容降到设计值的 67%，触发 `SIM_DECOUPLE_Z`；把上拉电阻由 4.7 kΩ 改到 100 kΩ，SDA 上升时间由 100 ns 升到 2118 ns，触发 `SIM_I2C_RISE`；给复位网络分别加 10 nF 与 1 µF 电容，时间常数落到 0.10 ms 与 10.00 ms，两个方向都被 `SIM_RESET_TAU` 抓住。反过来，当前这份正确设计上三条全部静默，没有误报。

### 4.6 消融实验 A–D

为回答"多智能体到底有没有用"，设计了 8 条测试需求 × 4 种配置的对照实验。四组配置逐级只增加一个变量：A 一次生成不返修；B 增加确定性规则修复；C 换成不看校验结果的模型评审；D 换成看校验结果的模型评审。为保证区分度，每个用例先注入一处**能被校验器检测到**的故障（去耦电容、I2C 上拉、复位上拉三者轮换），再交给各配置处理。

| 配置 | 说明 | 零错误率 | 平均错误 | 平均轮次 | 平均调用 | 平均 tokens | 平均耗时 | 选型准确率 |
|---|---|---|---|---|---|---|---|---|
| A | 单 Agent 一次生成 | 0% | 1.00 | 1.0 | 1.0 | 2027 | 12.1 s | 88% |
| B | 单 Agent + 规则校验器 | **100%** | 0.00 | 2.0 | 1.0 | **2283** | **16.3 s** | 100% |
| C | 多 Agent（评审无工具） | 0% | **1.75** | 1.75 | 3.75 | 12364 | 94.0 s | 100% |
| D | 多 Agent（评审带工具） | **100%** | 0.00 | 2.0 | 3.0 | 4447 | 34.8 s | 100% |

四条结论，其中两条对方案不利：

1. **不校验就一定带着错误交付**。A 组零错误率为 0%，注入的故障全部留在产物里。
2. **规则修复的性价比最高**。B 组只用 1 次调用就把错误清零，token 与耗时都不到 D 组的一半。能用确定性代码解决的问题，不应该交给模型。
3. **无工具的评审是负收益**。C 组零错误率 0%，平均残留 1.75 个错误，**比完全不修的 A 组（1.00 个）还多**——盲评审看不到真实问题，凭经验改，反而制造了新问题（只加器件不接线）；代价还是 D 组的 2.8 倍 token、2.7 倍时间。
4. **D 在本组故障上没有优势**。本轮注入的三类故障恰好都在规则覆盖范围内，所以 D 相对 B 只是更贵、没有更好。不做补充实验就宣称"多智能体更好"，是不诚实的。

### 4.7 补充实验 E：值错误与仿真闸门

上一节的第 4 条结论指出了实验设计的缺陷：故障类型太"容易被结构性规则发现"。因此补充了第二组实验：

- **故障类型改为 `value`**：把指示灯限流电阻改小 20 倍，**连接一点没动**。此时 ERC 0 错误、DRC 0 错误、11 条规则校验全绿。
- **新增配置 E**：与 D 完全相同，唯一差别是把仿真结论也送进返修闭环。

3 个用例实测（离线执行以排除模型抖动）：

| 用例 | 配置 | 结构错误 | 仿真错误 | 轮次 |
|---|---|---|---|---|
| C1 | B | 0 | **1** | 1 |
| C1 | E | 0 | **0** | 2 |
| C4 | B | 0 | **1** | 1 |
| C4 | E | 0 | **0** | 2 |
| C6 | B | 0 | **1** | 1 |
| C6 | E | 0 | **0** | 2 |

结论很直接：**B 组不是"通过"，只是"看不见"**。E 组用同样的返修逻辑，多了一份仿真证据，就把问题修干净了。这补上了 4.6 节的缺口——多智能体真正的价值不在于角色数量，而在于有没有给它一个能发现功能错误的工具。

一次完整的修复过程如下（`--inject-fault value`）：

```
注入故障：R2 改小 20 倍（值错误，连接不变）
R2 值 330 -> 16.5        # 故障态：指示灯电流 61.8 mA
R2 值 16.5 -> 203.94     # 按实测电流反推阻值，回到合规区间
闭环：2 轮，0 个错误
```

修复策略不是"乘 10 试一次"，而是按 I ∝ 1/R 反推：`R_new = R_old × I_实测 / I_目标`。

## 5 失败案例与讨论

课程要求报告包含失败案例。本节按"现象—根因—修法—如何防止复发"记录七个真实问题，其中五个来自真实模型输出，两个来自几何与数值细节。

### 5.1 案例一：模型给了 KiCad 官方库名，造出"半截设计"

**现象。** 评审 Agent 返回 `add_part` 时把符号写成 `Device:C`（KiCad 官方库名），而器件库里的 id 是 `pcbagent:CAP`。补丁执行时 `add_part` 解析失败被静默跳过，但紧随其后的两条 `connect` 照常执行，于是设计里出现了"接了线但器件不存在"的悬空引用 `C9`，一次产生 5 个校验错误，且模型在错误的基础上又改了两轮。

**根因。** 补丁执行不是原子的：失败的操作只是被记录，后续依赖它的操作仍然执行。

**修法。** 把 `apply()` 改成两阶段执行：第一阶段预解析全部 `add_part` 的符号与位号，解析失败的位号进入 `bad_refs`；第二阶段执行时，凡引用 `bad_refs` 的操作整组丢弃。同时给器件库加 KiCad 官方库名别名（`Device:C`、`Device:R`、`Device:LED` 等），把"可修复的不匹配"和"真的不存在"区分开。

**防止复发。** 新增测试 `test_unknown_symbol_rejects_whole_group`：断言未知符号时 `applied == 0`、`rejected == 3`，且原设计一字未改。

### 5.2 案例二：位号笔误导致白跑一轮

**现象。** 模型输出 `add_part ref=C1`，随后却是 `connect C8.1`。器件加进去了，连接接到了不存在的位号上，本轮补丁实际无效。

**根因。** 模型在同一次输出里对同一个新器件用了两个位号。

**修法。** 在本批补丁只有一个新增器件时，按前缀把笔误位号重定向到该器件；同时规定"没有 `add_part` 支撑的 `connect` 一律剔除"，杜绝悬空引用进入网表。

**防止复发。** `test_ref_typo_is_redirected` 与 `test_connect_to_ghost_ref_rejected` 两个用例锁定该行为。

### 5.3 案例三：只加器件不接线

**现象。** 用户要求"在 +5V 和 GND 之间加一颗 10uF 储能电容"，模型只输出了 `add_part`，没有 `connect`。器件被加进 BOM，但电气上完全悬空，而当时的规则只把它算作警告，闭环因此判定"通过"。

**根因。** 校验规则缺少"器件整体悬空"这一类，而它和"某个引脚悬空"是不同性质的错误。

**修法。** 新增 `PART_UNCONNECTED` 规则（错误级）：若某器件所有引脚都没有连接，判为建模错误而非"预留"；同时让追问修订路径也走返修闭环，实测从"留下 2 个错误"变成"2 轮自动接好 C8.1→+5V、C8.2→GND"。

### 5.4 案例四：首版原理图 17 个 ERC 错误

**现象。** 第一次用 `kicad-cli` 做真机检查时，ERC 报 17 个错误、43 个警告。

**根因与修法**（四类，逐条定位）：

| 违规类型 | 数量 | 根因 | 修法 |
|---|---|---|---|
| `pin_to_pin` | 1 | LDO 输出本身是 `power_out`，又叠加了 `PWR_FLAG`（也是 `power_out`），等于两个电源输出直连 | 只在"没有 power_out 驱动源"的网络上加 `PWR_FLAG` |
| `pin_not_connected` | 17 | 28 脚 MCU 的空置 GPIO 没有标记 | 每个悬空引脚写 `no_connect` |
| `endpoint_off_grid` | 21 | 坐标不在 1.27 mm 栅格上 | 器件坐标与引脚端点全部吸附栅格 |
| `lib_symbol_issues` | 20 | 无头 ERC 只读全局符号库表，读不到工程目录的 `sym-lib-table` | 符号已内嵌在原理图 `lib_symbols` 中，渲染与网表均正确，作为环境噪声过滤并在文档中公开说明 |

最后一条值得展开：尝试过把库表 uri 改成绝对路径、补 `.kicad_pro` 工程文件，均无效，这是 `kicad-cli` 的行为。处理方式不是假装没看见，而是在 `parse_erc_json` 中显式过滤并在 README 的"已知限制"里写明原因。四条修法后来都写成了测试，防止渲染器退化。

### 5.5 案例五：布通率只有 2/11

**现象。** 第一版自动布线只布通 2 条网络，其余全部失败。

**根因。** 给焊盘占位时用了"外接矩形 + 间距外扩"。DIP-28 相邻焊盘间距 2.54 mm、焊盘宽 1.6 mm，中间只剩 0.47 mm 走廊，矩形占位把走廊一起堵死，每个引脚都被围成孤岛，布线器无路可走。

**修法。** 改为按"格心到焊盘矩形的真实距离"判断是否被占用，走廊得以保留。

**结果。** 布通率从 2/11 提升到 11/11。

### 5.6 案例六：封装原点未吸附栅格导致短路

**现象。** DRC 报 GND 走线与 +5V 焊盘短路。

**根因。** 封装原点没有吸附栅格，DIP 焊盘中心落在 1.27 mm 的半格上（例如 38.73 mm），布线的占位判断整体偏移 0.63 mm，挡板刚好漏掉一条线。

**修法。** 封装原点与全部引脚端点吸附 1.27 mm 栅格。

**顺带的第二个坑。** 过孔只按一个格点占位，忽略了 0.8 mm 的实体，落在别人焊盘旁边就是一串间距违规。改为换层前检查 3×3 邻域。中间试过"禁止在任何焊盘上打过孔"的激进做法，布通率反而掉到 9/11——因为插针焊盘本就贯穿两层，同网络叠孔在电气上无害。最终回到"只禁止他人焊盘"，并接受 DRC 报出 6 个 `holes_co_located` 警告，把这个取舍写进文档而不是藏起来。

### 5.7 案例七：盲评审是负收益

**现象。** 4.6 节的 C 组（多智能体、评审看不到校验结果）平均残留 1.75 个错误，比完全不返修的 A 组（1.00 个）更差。

**根因。** 没有工具的评审只能凭经验猜测，而模型对"哪里可能有问题"的判断与真实问题几乎不相关；它倾向于"多补一点"，于是制造出只加器件不接线的 `PART_UNCONNECTED`。同时它的 token 消耗是 D 组的 2.8 倍。

**意义。** 这个负结果比任何正面结果都有价值：它证伪了"多 Agent 就是让几个模型互相看看"这种朴素理解，也解释了为什么本系统坚持"评审必须带工具"。

### 5.8 建模与评测的边界：先补模型，再加断言

工程上最容易犯的错，是把"测不出来"当成"没问题"。本系统最初对三条量选择不做，理由不是做不了，而是**直接做只会得到永远通过的假结论**：

| 最初没做的断言 | 直接测会怎样 | 补了什么模型 | 现在测什么 |
|---|---|---|---|
| 去耦阻抗 | 理想电容阻抗恒为 0，任何阈值都通过 | 电容串 12 mΩ ESR + 0.6 nH ESL | 1 A 电流注入下的 PDN 阻抗，折算为等效电容 |
| I2C 上升时间 | 只有上拉、没有总线电容，算不出时间常数 | 芯片引脚电容 + 10 pF 走线电容 | `.tran` 充放电的 30%→70% 上升时间 |
| 复位时间常数 | 目标设计只有上拉、没有电容，无 RC 可言 | 不补模型，改为"有 R+C 才测" | 有电容时测 63.2% 充电时间，否则显式标记不适用 |

第三条保留了"不适用"这个状态：本板的复位网络确实没有电容，断言不报错，但会把原因写进 `sim.json` 的 `extras.reset.reason`，命令行也会打印"复位时间常数：不适用（…）"。**既不假装通过，也不刷一条无意义的警告。**

同样的诚实原则贯穿其余近似：MCU 只用"电源脚等效负载 + GPIO 拉高"建模，按键默认断开，AREF 无内部基准，连接器与 PWR_FLAG 不参与仿真——这些全部写进结果文件的 `notes` 与 `unmodeled` 字段，而不是静默处理。

### 5.9 局限性与后续工作

1. **器件库规模小**。当前内置 10 个器件、4 个子电路模板，只覆盖最小系统类板卡。虽然已实现官方符号库导入（223 个库），但子电路模板仍需人工积累，这是回答"能不能设计带 WiFi 的板"时的真实瓶颈。
2. **布局质量不足**。贪心摆放导致板尺寸 185.8×78.6 mm，明显偏大；没有做 rip-up & reroute，拥挤时个别网络会布不通。
3. **时序与信号完整性只做到"点"上**。已有总线上升时间与 PDN 阻抗两项，但没有全链路时序、串扰与传输线阻抗匹配。
4. **过程记录不够均匀**。35 次提交集中在两个开发阶段，逐周 check-in 的痕迹不足，这是过程分的风险点。
5. **`live` 后端能力受限**。如 2.6 节所述，原理图侧没有对象模型，该后端只能做推送。

后续工作按优先级为：扩充子电路模板与器件库、把仿真扩展到温度与工艺角的多工况分析、补充容差（蒙特卡洛）评估，以及把布局从贪心改为带重叠代价的迭代优化。

## 6 结论

本文实现了一个从自然语言到 KiCad 原理图与 PCB 的完整智能体系统，覆盖课程全部五个基础步骤与四项进阶挑战。系统的核心不是"让模型画电路"，而是把模型限制在一个可校验的中间表示上：模型负责提议，确定性代码负责生成与把关。

三组量化结果支撑了这一判断：原理图与网表逐引脚一致（48/48）、ERC 与 PCB DRC 均为零错误、工作点仿真与手算一致。两组对照实验则给出了更有信息量的结论：规则修复的性价比高于模型评审；不带工具的评审是负收益；而把仿真结论接入闭环后，结构校验看不见的"值错误"才能被发现和修复。

最重要的经验是一条否定式结论：**多智能体的价值不来自角色数量，而来自工具**。没有工具，多个模型只会互相放大偏见；有了工具，一个模型加一份真实测量就足以定位问题。
